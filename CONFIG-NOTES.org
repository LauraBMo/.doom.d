** 2026-09-26 — TAB did nothing in a doc buffer: =[tab]= and ="\t"= are different key sequences
Reported from a live session as "evil-jump on tab", while =(key-binding (kbd "TAB"))= insisted
TAB was =forward-button=.  Both were true, because a TAB keypress arrives in *two* shapes that a
keymap lookup does not treat as one:
- a graphical frame delivers the VECTOR =[tab]=;
- a terminal, and =C-i=, deliver the STRING ="\t"= (character 9).
=(kbd "TAB")= is the string, so a binding written that way is one =key-binding' finds and a real
keypress never uses.  =julia-help-mode-map= bound the string; =config.org='s own =:n [tab]=
dispatch (Hlissner's "More handy TABs", added long before) binds the vector -- so the user's own
global binding answered every real TAB.  Fixed by binding *both* shapes, in
=julia-help-mode-map= and in =julia-help--link-keymap=.
- *Measured* in a daemon against the real config: =(key-binding [tab])= =evil-jump-item= while
  =(key-binding (kbd "TAB"))= =forward-button=, with the mode map holding no =[tab]= at all.
  After the fix both read =forward-button= in prose and on a link, S-TAB both
  =backward-button=, and RET on the link still =shr-browse-url=.
- *=key-binding= is not a substitute for pressing the key.*  Every probe that asked about the
  string form reported the binding was fine.  What settled it was =C-h k= on the real key, run
  by the user -- the one measurement no probe of mine was making.
- *Evil's own docstring is wrong here.*  =evil-make-overriding-map= says it gives "lower
  precedence than custom STATE bindings", but a bare =(define-key julia-help-mode-map [tab]
  ...)= was measured to beat the user's =:n [tab]= in =evil-normal-state-map=.  So a mode map can
  take a key back from a global state binding without an auxiliary keymap -- worth trying before
  reaching for =evil-define-key=.
- *Behaviour change to sanction:* in a doc buffer TAB now walks buttons rather than running
  =evil-jump-item=.  Outside those buffers the =:n [tab]= dispatch is untouched.
- The mutation script now refuses to run at all when the unmutated suite is red: one broken
  assertion had made all five mutants report CAUGHT, with the failure lines naming the broken
  test rather than the mutation.
Two testing lessons, both surfaced by that check and neither by reading:
- *A test that checks one shape of a key is not testing the key.*  =julia-help-test--tab-runs-p=
  asserts both shapes now.  Every assertion it replaced passed while the real key did nothing.
- *The test fixture had to become a real doc buffer.*  Without the mode, TAB resolved through
  =button-map= on the string form and found *nothing* on the vector form -- so the fixture was
  the reason the gap was invisible.  Mode first, content inside =inhibit-read-only=, exactly as
  =julia-help--display= does it (the other order lets =julia-help-mode= run
  =kill-all-local-variables= and wipe the buffer-local follow function linkify just set).
- *A mutation must break the thing, not a neighbour.*  ="s/'keymap button-map/'keymap nil/="
  *removes* shr's keymap as well, so RET fell through to the mode map and still worked.  It only
  looked caught while the fixture had no mode map; the moment the fixture became a real doc
  buffer it started MISSing.  The faithful mutation deletes the =put-text-property= and leaves
  shr's keymap in place.


** 2026-09-25 — Tidal's ghci could not find the package outside =~/src/tidal-music=
Tidal 1.10.2 was installed with =cabal install --lib tidal --package-env .= run inside
=~/src/tidal-music=. That does **not** register tidal in the global package db: it writes
=~/src/tidal-music/.ghc.environment.x86_64-linux-9.10.3=, pointing at
=~/.local/state/cabal/store/ghc-9.10.3-inplace/package.db=. GHC reads that file from the
current directory **or a parent, never from =$HOME=** — so the package was reachable only from
under =~/src/tidal-music=, and nowhere else on the machine.

The symptom looks like a different bug. Opening a =.tidal= file in =~/Dropbox/Music/= and
pressing =C-c C-s= starts ghci normally, then the boot script dies at =import
Sound.Tidal.Boot=. Nothing plays and there is no error until you read the =*tidal*= buffer.

Fix — give GHC an environment file it reads from any directory:
#+begin_src shell
ln -sfn ~/src/tidal-music/.ghc.environment.x86_64-linux-9.10.3 \
        ~/.ghc/x86_64-linux-9.10.3/environments/default
#+end_src
=-n= is the part that is not optional: with =default= already a symlink to a directory, plain
=ln -sf= writes a link *inside* the target instead of replacing it. =-r= (store the link target
relative) is a reasonable addition and costs nothing.

Two things that made this harder to guess than it should have been:
- The GHC user guide documents only the XDG path
  (=$XDG_DATA_HOME/ghc/<arch>-<os>-<ver>/environments/default=) as read automatically, and does
  **not** list =~/.ghc/<arch>-<os>-<ver>/environments/default=. GHC 9.10.3 honours both. Verify
  against the binary, not the document.
- =ghci= exits **0** even when the module is missing, so the exit code is worthless here. Assert
  on the output line: =:t fast= must print =fast :: Pattern Time -> Pattern a -> Pattern a=.
  Checked from =/tmp=, =~/Dropbox/Music= and =~/Dropbox/Music/Curse1=.

Related, and not a fault: =d1=, =d2=, =hush= and =cps= come from =Sound.Tidal.Boot= — pulled in by
the =:script= line that points at =BootTidal.hs= — and **not** from =Sound.Tidal.Context=. A bare
ghci knows =fast= but not =d1=. That is expected, not a broken install.

Repeating this after a GHC upgrade: the compiler version sits inside every path involved
(=~/.ghc/x86_64-linux-9.10.3=, the =.ghc.environment.*= filename, =store/ghc-9.10.3-inplace=), so
re-run =cabal install --lib tidal --package-env .= in =~/src/tidal-music= and re-run the =ln -sfn=
above — a cabal rewrite of the env file can break the symlink. Neither path needs root, and
=~/.local/share= is not system-managed here.

** 2026-09-25 — the ispell-then-abbrev helper was dead code; ported to jinx
=*** TODO Endless ispell & abbrev= in =config.org= was parked (=:tangle no=) and its =l i=
hydra head commented out: the port of endlessparentheses' "Ispell and abbrev" ran on =flyspell=
overlays and =ispell-get-word=, and this config spells with =jinx= now (=global-jinx-mode=,
=ispell-word= remapped to =jinx-correct=). Ported and un-parked; the head is
=:desc "jinx & abbrev" "i" #'brust-jinx-word-then-abbrev=.

What it does, and the three jinx internals it stands on — all verified by reading
=jinx.el=, none of them public API, so a jinx upgrade that renames them breaks this *loudly*
(a void-function) rather than quietly:
- misspellings are the overlays jinx tags with 'category =jinx-overlay= (=jinx.el:525=), and
  =jinx--get-overlays= (=:531=) returns them already rotated to start at point;
- =jinx--bounds-of-word= (=:869=) is the word at point, where the original used
  =ispell-get-word=;
- =jinx--correct-overlay= (=:784=) corrects one overlay and **returns nil either way** — so
  "was it corrected?" has to be read off the text. The *public* =jinx-correct-word= (=:1093=)
  loops to the next word, which is why it is the wrong tool here: after it, there is no telling
  which word the abbrev should be taught.
Also of note: =jinx--correct-guard= kills jinx's re-check timer for the duration, so the overlay
list cannot go stale mid-loop, and it turns =jinx-mode= on in the buffer if it was off.

The abbrev is the point of the whole thing — it makes the typo fix itself from then on — and it
is engine-agnostic: =abbrev-mode= is on by default here and =save-abbrevs 'silently= with
=abbrev-file-name= → =~/Dropbox/config/abbrev-def.el= (=config.org=, above the block) already
handled persistence.

- *Verified* (2026-09-25) in a live session, on a displayed temp buffer (jinx only checks the
  window's visible text, so an undisplayed buffer finds nothing and reports "no misspelled word"
  — that cost one confusing run). With only =completing-read= stubbed and a throwaway abbrev
  table: two typos, answer the first unchanged → it is skipped and *not* taught; answer the
  second → the text is corrected and =brownn= → =brown= is defined, locally for a prefix arg and
  globally otherwise. Nothing misspelled signals an error and defines nothing — with jinx's own
  "No misspelled word in visible text", which surfaces before this command's own message.
- *Trap that cost two rounds, worth repeating:* writing this block by hand, the outer =let= was
  closed one paren early. The *count* was then balanced by luck, so =read= returned a complete
  form and only the "next form" check showed a stray paren; after trimming it, the *nesting* was
  still wrong and the command died with =void-variable fix=. Paren counting by eye is not a
  check. What catches it is reading the form and asserting its *shape* — outer =after!=, two
  =defun=s, body =(docstring interactive let)=, let body =(save-excursion unless define-abbrev
  message)= — which is also how the block was finally written: into a scratch file, checked
  structurally in =emacs -Q --batch=, then spliced in whole rather than patched. A splice that
  inserts at =line-end-position= also put =(after! jinx= on the =#+BEGIN_SRC elisp= line, which
  shifted every form that was then read from there — grep for the merged line, not for the fix.

** 2026-09-25 — the window rule asks what is being *read*; the two doors are gone
Supersedes the two entries this replaces: a =*helpful*= link and a Doom-dashboard click each split
a single-window frame, and each was answered with a *door* — =display-buffer-overriding-action=
bound around one specific call. Both doors, and everything holding them up, are removed; the rule
itself now knows about reading.

- *Why doors were needed at all:* the policy is a match-all entry at the top of
  =display-buffer-alist=, which outranks even the action a caller passes explicitly, so "the same
  window please" from =find-file= went unheard and every case wanting it back needed an escape hatch
  *plus* a way to decide when it applied — two =defconst=s, five =defun=s, an =with-eval-after-load=
  and two advices. The action order itself is in *Tricks*.
- *What replaced it.* The rule asks about the **selected window's buffer**: a buffer in
  =my/in-place-modes= (helpful, =brust-julia-doc-mode=, =+dashboard-mode=) takes the pane it was asked
  from instead of the pane beside it; =my/in-place-window-p= is that test, and it keeps the old guard
  that a *dedicated* selected window is never written into. One question, the same for all three
  callers, so nothing else is needed: =helpful-switch-buffer-function= is back to its own default
  =#'pop-to-buffer= (=helpful.el:135=), =helpful--navigate= and =+dashboard/push-button= are
  unadvised, and the four Julia call sites call plain =pop-to-buffer= again.
- *The cost, accepted, and now a case of its own:* the trigger is "documentation is being read here",
  not "the call came through this door", so a buffer arriving while the docs sit in the *left* pane
  takes **that** pane rather than the one beside it (=H6b=). Where the docs are rightmost nothing
  widened — the policy took that pane anyway.
- *Verified* (2026-09-25), three ways: =local/tests/window-policy-test.el=, 26 checks, all pass
  (1-8 the policy, =5b= the dedicated selected pane, =H1-H7= the real helpful, =D1-D4= the
  dashboard's =find-file=); =local/tests/julia-doc-test.el= passes and no longer reads the policy
  block at all; and a *freshly started* Emacs
  (=~/.claude/test-scripts/-home-laury--config-doom/fresh-window-policy.sh=) passes 13 checks against
  the loaded config on a real frame — including that the catch-all is still first in
  =display-buffer-alist= once every Doom module has had its say.
- *Not covered:* the real dashboard buffer — the harness stands in for it with =+dashboard-mode= on
  another buffer, so "the dashboard's own buffer carries that mode" is read by eye. What was measured
  live instead is that both modes are real: =(get '+dashboard-mode 'derived-mode-parent)= →
  =special-mode=, and the same for =brust-julia-doc-mode=. And with *every* window of the frame
  dedicated there is nowhere legal to put the buffer, so the default chain decides.

** 2026-09-15 — the fold keys did nothing in a .tex or a .jl, in three separate ways
The hydra Fold columns (=z= / =Z= / =A=) had been added the day before and did nothing. Three
faults at once, all silent, all written up under *Tricks* below: `hs-minor-mode' was never on

** 2026-09-15 — a mode hook added inside `after!' arrives too late for the first buffer
The hook that was supposed to turn `hs-minor-mode' on lived in =(after! latex …)= /
=(after! julia-repl …)=. It was *in* the hook variable — and the first buffer of each mode
still came up with the mode off, in a freshly started Emacs. Cause: registering that hook is
one of the things that *loads* AUCTeX / julia-repl, so the `after!' body runs in the middle of
the first buffer's own `run-mode-hooks', and Emacs does not run a hook that was added
mid-run. Every later buffer gets it; only the first one of the session misses.

- *Fix:* register the hook at top level, outside any `after!'. Both of ours moved there.
- *How it was caught:* a daemon started from the shell, because an in-session check cannot see
  this — by then the hook is already installed (the first attempt at verifying this was
  invalid for exactly that reason). The probe that does work:
  #+begin_src sh
  emacs --init-directory ~/.config/emacs --daemon=probe
  emacsclient -s probe --eval '(with-current-buffer (find-file-noselect "/tmp/x.jl") (bound-and-true-p hs-minor-mode))'
  #+end_src
  Note =--batch= is *not* equivalent: language packages do not load there, so a =.jl= opens in
  =fundamental-mode= and a =.tex= in the built-in =latex-mode=, and the check proves nothing
  about the real config.

** 2026-09-15 — a Julia =export= block cannot be delimited by trailing commas
=brust-julia-update-exports= now rewrites the block in place (it used to append a second one).
Finding the old block is the fiddly part: the previous format put one name per line with no

** 2026-09-13 — latex-mcp: fails to connect with "No module named 'mcp.server.fastmcp'"
=claude mcp add --scope user latex -- uvx latex-mcp= registers fine, but =claude mcp list= then
reports =latex: ... ✘ Failed to connect — -32000: MCP error -32000: Connection closed=. Running
=uvx latex-mcp= by hand shows the real error:

#+begin_src sh
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where
FastMCP was renamed to MCPServer ... or pin 'mcp<2' to keep running v1 code.
#+end_src

- *Root cause:* latex-mcp 0.2.0 declares =mcp[cli]>=1.26.0= with *no upper bound*, so =uvx=
  resolves the latest =mcp= (2.x), where =mcp.server.fastmcp.FastMCP= was renamed to
  =mcp.server.mcpserver.MCPServer=. Upstream packaging bug, not a fault in this config — and
  *nothing to do with Docker*, which is where the original diagnosis was pointed.
- *Fix:* pin the dependency in the registration itself:
  =claude mcp add --scope user latex -- uvx --with 'mcp<2' latex-mcp=
  Stored in =~/.claude.json= as ="args": ["--with", "mcp<2", "latex-mcp"]=. The pin is required
  until upstream bounds the version; re-check when latex-mcp releases next.
- *Also note:* =uvx latex-mcp= needs *no container at all*. The package's own code resolves
  compilers with =shutil.which= (=latex_mcp/core/command.py=). Docker appears only in the
  README's *alternative* config, which containerises the whole server
  (=docker run -i --rm --mount type=bind,src=${PWD},dst=${PWD} -w ${PWD} ghcr.io/sepinetam/latex-mcp:latest=).
  The two routes are different commands — don't conflate them.
- *Gotcha:* the =latex_compile= tool defaults =working_dir= to =/workspace= — a leftover from the
  container route. =/workspace= does not exist on this host, so callers must pass an explicit
  =working_dir= or the call fails.
- *Verified:* raw JSON-RPC probe (=initialize= + =tools/list=) returns 3 tools —
  =latex_compile=, =latex_list_compilers=, =latex_clean=. =latex_compile= on a real =main.tex=
  returned =success: true= and wrote a 38 KB PDF; =latex_list_compilers= reports the host TeX Live
  (=pdflatex=, =xelatex=, =lualatex=, plus =bibtex=, =biber=, =makeindex=, =latexmk=,
  =latexmk_available: true=).
- *Lesson:* =claude mcp list= showing "✔ Connected" is only a handshake. A server that dies at
  import reads as a connect error there — probe =tools/list= to confirm it actually serves tools.

** 2026-08-17 — pdf-tools: =j=/=k= scroll snaps back to top of page every few presses
In =pdf-view-mode= with =pdf-view-roll-minor-mode= on, holding =j= (or =k=) scrolled
fine for ~4–5 presses, then jumped back to the beginning of the current scroll.
=s-j= / =s-k= (single-line scroll) always worked.

- *Root cause:* =j=/=k= were bound to =brust-pdf-view-next-line-or-next-page-5=, which
  did =(brust-by-five #'pdf-view-next-line-or-next-page args)= — a =funcall-interactively=.
  The =funcall= bypasses roll-mode's keymap remap (=pdf-roll.el:353=,
  =[remap pdf-view-next-line-or-next-page] -> pdf-roll-scroll-forward=), so it ran the
  real command body, which under roll mode is =(dotimes (_ arg) (pdf-roll-scroll-forward))=
  — i.e. it called the roll scroller *5 times in a tight loop with no redisplay between
  calls*. =pdf-roll-scroll-forward= reads the *live* =window-start= / =window-vscroll=
  (=pdf-roll.el:278,292=), which only refresh on redisplay. Within one page the stale
  reads harmlessly accumulate; crossing a *page boundary* leaves =pdf-view-current-page=
  and vscroll inconsistent, and the next redisplay's =pdf-roll-pre-redisplay=
  (=pdf-roll.el:224=) snaps =window-start= back to =(pdf-roll-page-to-pos page)= — the top
  of the page. =s-j= worked because the remap makes one keypress = one scroller call.
- *Fix:* call =pdf-roll-scroll-forward= / =pdf-roll-scroll-backward= directly with a count
  of 5 (a single correct multi-line pass — the library already takes an =n= arg,
  =pdf-roll.el:275=) instead of looping the high-level command. In =config.org=, the two
  =brust-pdf-view-*-line-or-*-page-5= functions now branch on
  =(bound-and-true-p pdf-view-roll-minor-mode)=: under roll mode
  =(brust-by-five #'pdf-roll-scroll-forward args)=, else the old
  =(brust-by-five #'pdf-view-next-line-or-next-page args)= (fine for non-roll: single call).
  Routing through =brust-by-five= keeps its =(if (numberp args) (* 5 args) 5)= nil-guard.
- *Lesson:* =pdf-roll-scroll-forward= is not safe to call repeatedly within one command;
  pass it a count and let it do one pass per redisplay. Verified working by the user after
  =doom sync= + reload.

** 2026-09-25 — under =batch-byte-compile=, neither =load-file-name= nor =buffer-file-name= is set
A file that puts its own directory on =load-path= with a bare =add-to-list= cannot
be byte-compiled.  The compiler *evaluates* a top-level =(require …)= -- it has to,
to get macros -- but does not evaluate the =add-to-list=, so the require fails
with =Cannot open load file= while *loading* the very same file works fine.  Which
variable holds the path is not guessable; measured:

#+begin_src elisp
(eval-and-compile
  (message "load-file-name=%S buffer-file-name=%S byte-compile-current-file=%S"
           load-file-name buffer-file-name (bound-and-true-p byte-compile-current-file)))
#+end_src

prints =load-file-name=nil buffer-file-name=nil byte-compile-current-file="/abs/x.el"=.
So the fix takes all three, =eval-and-compile=d, and guarded by a =when= -- any of
the three can be nil, and =file-name-directory= on nil signals.  Three smaller
traps from the same file, all cost time:
- =ert-deftest= takes its docstring *positionally* -- =(ert-deftest name () "doc"
  body…)= -- not as =:doc=, which dies as "Keyword argument :doc not one of
  (:expected-result :tags)".
- =princ= prints nothing inside =eval-and-compile= under =batch-byte-compile=,
  because byte-compile rebinds =standard-output=.  Use =message=.
- =provided-mode-derived-p= returns the mode *symbol* it matched, not =t=.  A test
  written to expect =t= fails on a correct package.


** 2026-09-25 — what a match-all =display-buffer-alist= entry outranks
=display-buffer= tries its actions in this order (=window.el:7924=):
=display-buffer-overriding-action=, the matching =display-buffer-alist= entry,
=display-buffer--special-action=, *the ACTION argument the caller passed*, then
=display-buffer-base-action= and =display-buffer-fallback-action=. So a match-all entry at the top of
the alist beats even =find-file=, whose "same window" arrives as that ACTION argument through
=pop-to-buffer-same-window= — which is why the window policy's exceptions used to need
=display-buffer-overriding-action= around each caller. What covers all of them instead is asking the
rule about the *selected window's buffer*: the source buffer is current and selected when a click or
a link displays something (=window-normalize-buffer-to-switch-to= does not =set-buffer=,
=window.el:9013=), so "what is being read here" is answerable from inside the rule.

- The same function in =display-buffer-base-action= would leave every explicit wish alone — the
  caller's action *and* every other alist rule — the better seam when the policy is a default rather
  than the law. Not used here because it applies only where nobody else has an opinion, so anything
  displaying itself with a plain =pop-to-buffer= (a REPL, the dashboard's agenda and mail items)
  would still need a door.

** 2026-09-25 — a help buffer's own keys never fire: they are in the major-mode map, and evil's normal state answers first
Measured in a live =*helpful function: car*= buffer: =(key-binding "l")= is =evil-forward-char=, =("n")=
is =evil-ex-search-next=, =("p")= is =ignore=. Doom binds =l=/=r= in =helpful-mode-map= to
=+emacs-lisp/helpful-previous=/=next= (=modules/lang/emacs-lisp/config.el:320-321=) and helpful binds
=n=/=p= to the button commands, and *none of it fires* — those buffers open in evil's normal state, and
a minor-mode map outranks the major-mode one (the entry on =cdlatex-mode-map= is the same trap). =TAB=
works only because evil never claims it, and RET on a link works from the other side: the button's
text-property keymap outranks evil too.
Fixed by *giving the mode maps precedence* rather than repeating every key for the state:
=evil-make-overriding-map MAP 'normal= ("Give KEYMAP precedence over the global keymap of STATE"). Each
mode's own bindings then fire, defined once, and the doc buffer's keys are back where the mode is. This
was the first version's mistake — =evil-define-key 'normal= for three maps duplicated every binding and
ran 24 lines.
Three things learned doing it, each measured. (1) A =g= *prefix* in an overriding map costs nothing:
=gg'/=G= still fall through to evil, so =gr= works for revert — verified by pressing the keys and watching
point move, not by reading =key-binding=. A *bare* =g= binding would not fall through, which is why
=helpful-mode-map= has its own single =g= (update) cleared in favour of =gr=. (2) A check that reads the
keymap object proves nothing: =lookup-key= on =brust-julia-doc-mode-map= returned =forward-button= for TAB
while the live buffer answered =evil-forward-char= for =l=. Ask the live buffer — =(key-binding KEY)= with
the mode in the state it really opens in. No =--batch= test can see this, because evil is not there.
(3) State bindings outrank an overriding map, so a stale =evil-define-key 'normal= in the session masks
the new mechanism entirely while debugging: clear the map's auxiliary keymap
(=(evil-get-auxiliary-keymap MAP 'normal nil nil)=, then =define-key ... nil=) before believing a reading.

** 2026-09-25 — an empty JSON field is not an absent one, and elisp will happily print it
=Markdown.MD= for a docstring fetched with =?help= has *nothing* attached to it: that path goes through
=REPL.helpmode=, which displays an MD of its own making, so =:binding=, =:typesig= and =:results= are all
missing (measured: =?sin= sends =symbol/binding/module/typesig = ""= and no results, while the docstring
HTML is perfectly good). The payload is built by a serializer that writes =""= for a field it has nothing
for — and *an empty string is true in elisp*, so every guard of the shape =(when field ...)= passed. The
buffer came out named =*julia-doc: *= after the empty symbol, opening on a blank heading line, with
"="Defined in:  "= and "="Signature:   "= printed with nothing after them.
Two fixes, and keep both. The sender now writes =null= for an empty field (=json_or_null=), and the
receiver treats =""= as absent anyway (=brust-julia-doc--nonempty=), because a half-updated Julia still
sends the old form. The check worth keeping is on the rendered buffer: its first line is the first
heading, and no line matches =^\(Defined in:\|Signature:\|Methods\)\s*$=. In general: "absent" and "empty"
are different things on either side of a serialization boundary, and in elisp guard on =(equal x "")= or a
helper, never on truthiness alone.

** 2026-09-25 — shr draws links as buttons that have no action, and =make-text-button= will not take over shr's keymap
=shr-render-region= puts a =button= property on link text that *is* marker-backed, so =button-at=
and =next-button= / =forward-button= do find those links. What they do not have is an =action=:
=push-button= on one signals =void-function nil=.
Following the link does not go through the button at all. shr also sets the text's =keymap= to
=shr-map=, which sends RET and mouse-2 to =shr-browse-url= — and a text-property keymap outranks
the buffer's major-mode map, so binding RET to =push-button= in the mode does *nothing* while
point is on a link.
Retargeting one therefore needs two lines, not one: =make-text-button= to supply the action, and
=put-text-property ... 'keymap button-map= to take the keymap back. =make-text-button= will not
replace a keymap that is already on the text. Do only the first and the link is found by
=button-at= and fires under =push-button= while RET still runs =shr-browse-url= — half fixed, and
a test that inspects properties instead of following the link passes it. The check that bites is
=(key-binding (kbd "RET"))= with point on the link, against =push-button=.
*And the same keymap swallows TAB, but only on the links shr keeps.*  =shr-map= is put on every
*link span* (=shr.el:1338=, "Don't overwrite any keymaps that are already in the buffer"), and it
binds TAB -- and C-i, one and the same event -- to =shr-next-link=.  So TAB reached the mode map in
the prose and on a cross-reference (whose keymap is replaced), but on any link shr kept -- a URL in a
docstring -- it ran shr's link walker instead of =forward-button=.  Reported from a live session as
"tab still does not work", and it was the *partial* nature that made it hard to see: an empty test
buffer has no links at all, so TAB looked fine there.  Fixed with
=julia-help--retarget-shr-links=: a keymap whose parent is =shr-map= with TAB / =[backtab]=
overridden, written over each span whose =keymap= property *is* =shr-map=, so RET still browses.
Two traps in testing it, and the mutation check caught both -- reading did not:
- *A position one character past the link is outside the span.*  =search-forward "docs"= leaves
  point after the link text, where shr's keymap no longer applies, so TAB reads =forward-button=
  there even against a fix that does nothing.  Check *inside* the link, at both ends.
- *A mutation can invert a guard rather than disable it.*  =(eq (get-text-property pos 'keymap)
  nil)= is not "never true" -- it is true wherever there is *no* keymap -- so the mutant went on
  producing =forward-button= and read as a caught mutation.  Disable a guard with a value the
  property can never hold.
The mutation script had to learn the same lesson: a run that fails *without naming a failing test*
proves nothing, and an unbalanced test file made all four mutants look caught.  It reports SUSPECT
for that now.
Two smaller things from the same afternoon. =text-property-any= compares with =eq=, so it never
matches a string value — walk with =next-single-property-change= instead. And =shr-render-region=
reflows differently under =--batch= (one word per line) than it does in a live window, so a
rendered buffer printed by a batch test is not what the user will see; check layout in a real
Emacs before believing it.

** 2026-09-25 — a buffer that is not there reads as an empty one
=(get-file-buffer FILE)= returns nil when the file is simply not open — and =(buffer-modified-p
nil)=, =(buffer-size nil)= and the rest then quietly answer about the *current* buffer instead of
signalling. On 2026-09-25 that cost real time: a size read this way (168,076, from a hidden
= *tangle config*= buffer) was compared against =config.org= on disk (252,775) and read as
"a bad edit truncated the buffer", and the user was told to revert work that had never been
damaged. There was no =config.org= buffer open at all. Bind the buffer first and test it —
=(when-let ((b (get-file-buffer f))) ...)= — and remember that a number coming back is not
evidence that the thing you asked about exists. This is the same shape as a tool reporting
success while it lied: check the subject, not just the reading.

** 2026-09-25 — the =51;E= vterm escape: whitelisted commands, unquoted arguments
=vterm-eval-cmds= is a whitelist, and a name that is not on it only prints "Failed to find
command" — a new command goes in that list, which is why the doc entry point is registered there.
Arguments are split with =split-string-and-unquote=, which *unquotes* =\"= and =\\=; a raw JSON
argument would be mangled in transit, so the payload travels base64 (which has no whitespace and
no backslashes). Measured rather than assumed: at the moment =vterm--eval= runs, =(current-buffer)=
is the vterm buffer — that is how a doc buffer learns which REPL to send =@doc= back to.
Testable without Julia at all: in a vterm buffer, send
=printf '\033]51;E<command> <args>\033\\'= and the escape is parsed and dispatched.

** 2026-09-15 — Folding: evil's keys, Doom's module, hideshow's rules, no LSP anywhere
The keys are evil's own, in normal state, and need no binding: =za= adds or removes the fold
at point, =zc= / =zo= close and open one, =zO= opens recursively, =zr= / =zm= do the whole
buffer (=evil-maps.el:87-92=). What a keypress *runs*, though, is not evil's command: with
=:editor fold= enabled (=init.el=, since 2026-09-15) evil's fold commands are remapped to
Doom's =+fold/toggle= and friends, which prefer vimish-fold, then outline, then treesit, then
hideshow, and which call =+fold--ensure-hideshow-mode= first — so `hs-minor-mode' comes on in a
buffer the first time a fold key is used there, and never at buffer open. That is what replaced
the eager =julia-mode-hook= this config carried for a few hours, and it is why no hook is
needed now.

So if the mode is not the question any more, the *rule* is, and three more things still have to
be true. Every one of them fails silently:

1. *A hideshow fold needs a rule for the buffer's mode.* =hs-hide-all= and its siblings are
   wrapped in =hs-life-goes-on=, =(when hs-minor-mode …)= — called with the mode off they
   return without a message, which is what made folding look broken rather than misconfigured
   before the module was on. LaTeX does not rely on any of this: folding in those buffers is
   AUCTeX's =TeX-fold-mode= (=add-hook 'TeX-mode-hook #'TeX-fold-mode= — =LaTeX-mode= runs that
   hook as well, =latex.el:8419=), on the =C-c C-o= prefix: =C-o= dwim, =C-e= environment,
   =C-m= macro, =C-s= section, =C-b= buffer, with lowercase =b= / =r= / =s= to unfold. =za= in
   a .tex folds *sections* through outline, and off a heading it switches hs-minor-mode on and
   folds nothing — harmless, but it is why the mode can turn up in a .tex you folded in.
2. *The buffer must have an entry in `hs-special-modes-alist'.* =hs-grok-mode-type= looks it
   up with =(assoc major-mode …)= — an *exact* symbol match, no =derived-mode-p=. An AUCTeX
   buffer's mode is =LaTeX-mode=, so Doom's =:editor fold= entry, keyed =latex-mode=, could
   never have matched even if that module were enabled. The same function refuses with "Mode
   doesn't support Hideshow" unless *both* =comment-start= and =comment-end= are bound in the
   buffer (Julia has ="# "= and =""=, so it passes).
3. *lsp-mode is not in this loop at all.* =lsp-enable-folding= sounds like a bridge to
   hideshow; it is not. Nothing in the whole lsp-mode repo mentions hideshow; the variable
   only registers lsp-mode's own =lsp--folding-range= thing-at-point property. Measured on
   =mm.tex=: texlab offers 15 folding ranges and not one reaches hideshow. What folds is the
   regexps in the entry — =hs-block-start-regexp= / =hs-block-end-regexp= — and nothing else.
4. *For a keyword-delimited language, the entry's FORWARD-SEXP function is not optional.*
   The default is =forward-sexp=, which from =function= merely steps over the word, so nothing
   folds. (The popular one-line recipes that pass =nil= in that slot do not work.) Julia got
   =brust-julia-hs-forward-sexp=, a small counter that walks block keywords down to the
   matching =end=. Its two regexps are anchored to =^[ \t]*= so =A[end]=, an index rather than
   a block, is not counted as one; verified with =function= at 1 folding 1→9, the inner =for=
   folding 3→5 and the inner =if= folding 6→8, with =x[end]= sitting in the middle of the first.

Four traps met while writing this:

- =#'foo= inside a *quoted* alist entry is data: ='((julia-mode … #'brust-julia-hs-forward-sexp
  nil))= hands hideshow the list =(function brust-julia-hs-forward-sexp)=, and folding signals
  =Invalid function: #'brust-julia-hs-forward-sexp=. Pass the bare symbol. Doom's latex entry
  passing a =(lambda …)= works only because a lambda list is already funcallable.
- =hs-hide-block-at-point= returns a *position* (the value of its last =goto-char=), not the
  overlay, and =nil= when it does not fold. Reading it as an overlay gives
  =Wrong type argument: overlayp= on a fold that in fact happened; collect
  =(overlays-in (point-min) (point-max))= and filter on the =hs= overlay property instead.
- *A remap only happens in the command loop.* With =:editor fold= on, =za= runs
  =+fold/toggle=; but calling =(evil-toggle-fold)= as a *function* — from a probe, or from
  =M-x evil-toggle-fold= — goes straight to evil's own command, which consults
  =evil-fold-list= itself and, with no fold mode active, dies with "Enable one of the following
  modes for folding to work: …". That is a different code path, and an earlier check of mine
  measured it and drew the wrong conclusion about the module. Test the key path
  (=(funcall '+fold/toggle)=) if you want to know what =za= does.
- *`hs-minor-mode' is buffer-local*, so reading it without =(with-current-buffer BUF …)=
  reports nil from whatever buffer happens to be current — which is exactly how a verified
  "the hook did not fire" reading was produced from a buffer where it would have said ON.

Checking a fold instead of eyeballing it: ask the server for its own numbers and compare what
ends up hidden —
#+begin_src elisp
(mapcar (lambda (r) (cons (line-number-at-pos (lsp--folding-range-beg r))
                          (line-number-at-pos (lsp--folding-range-end r))))
        (lsp--get-folding-ranges))
#+end_src
For =\begin{itemize}= at line 118 in =mm.tex= texlab says 118→122 and the hideshow fold hides
lines 119–122: the same region, so the regex rule agrees with the server here. (Note
=lsp--get-folding-ranges= returns =lsp--folding-range= *structs*, not plists — =plist-get= on
them silently yields nil, which reads like "no ranges".)

** 2026-08-17 — Force new buffers to split side-by-side (new buffer on the right)
Goal: work with two windows, current buffer on the LEFT, the new one (terminal,
Claude Code, julia-repl, PDF...) on the RIGHT. Buffers were instead opening stacked
(top/bottom), or in the same window.

- *Why it happened:* Emacs =split-window-sensibly= tries a side-by-side split first,
  but only if the window is at least =split-width-threshold= columns wide (default
  *160* — wider than most frames), so it fell back to a stacked top/bottom split.
  This is a plain-Emacs =display-buffer= behaviour, and it applies here because Doom's
  =:ui popup= module is *disabled* (see =init.el=) — with popup on, that module would
  intercept these buffers instead and this recipe would not apply.
- *Global fix* (in =config.org=, just after the Evil split settings):
  #+begin_src elisp
  (setq split-width-threshold 80    ; allow side-by-side when window ≥ ~80 cols
        split-height-threshold nil) ; never auto-split top/bottom — force side-by-side
  #+end_src
  New buffer lands on the right (=split-window-right= semantics), current stays left.
  Bump =80= up if you want each half wider before Emacs is willing to split. *Corrected
  2026-09-24:* on a frame too narrow to split, Emacs reuses an existing window only when
  there are *two or more* windows; a *sole* window gets split anyway, stacked — see the
  correction in the 2026-09-24 entry below.
  Verified: julia-repl, Claude Code, and LaTeX =C-c C-v= (PDF) all split right.
- *Note:* =split-height-threshold nil= means Emacs will never *auto*-create a stacked
  split anymore; manual evil splits are unaffected (=evil-vsplit-window-right t=).

*** If some mode STILL splits stacked (or opens in the same window)
A few commands bypass =split-window-sensibly= — they hard-code =switch-to-buffer=
(same window) or pin their own direction. The global thresholds can't reach those.
Fix that one mode with a targeted =display-buffer-alist= rule (=display-buffer-in-direction=
forces the side regardless of thresholds). Match on major mode or on a buffer-name regexp:
#+begin_src elisp
(add-to-list 'display-buffer-alist
             '((derived-mode . some-offending-mode)   ; or e.g. "\\*Some Buffer\\*"
               (display-buffer-reuse-window display-buffer-in-direction)
               (direction . right)
               (window-width . 0.5)))
#+end_src
Find the mode with =C-h m= in the misbehaving buffer, or the exact buffer name with
=C-x C-b=. (We had this ready for LaTeX's PDF viewer but the global fix already covered it.)

** 2026-09-24 — Never more than two windows: a new buffer takes the other pane
Follow-on to the entry above. With two panes already open, a command that shows a new
buffer (new Claude Code session, julia-repl, help...) split the frame a *third* time
instead of using the pane that was already there. Wanted: the pane on the RIGHT of the
selected window; if the selected window is already the rightmost, take over that pane;
split only when the frame has a single window.

- *Why it happened:* the default action chain cannot express "the other pane".
  =display-buffer--maybe-pop-up-frame-or-window= splits whichever window it likes — third
  window included — and it runs *before* =display-buffer-use-some-window=; and that latter,
  with =inhibit-same-window= nil, counts the selected window as its best "second best"
  candidate, so it hands back the window you are already in. No threshold tuning reaches
  this — =split-width-threshold= only decides whether a split is possible, never which
  window gets used.
- *Fix* (in =config.org=, just below the thresholds above): an action function plus a
  match-all rule, so every =display-buffer= call obeys it.
  #+begin_src elisp
  (defun my/display-buffer-max-two-windows (buffer alist) ...)
  (add-to-list 'display-buffer-alist
               '("\\`" my/display-buffer-max-two-windows)) ; every buffer name
  #+end_src
  Order matters: =add-to-list= and =push= both *prepend*, so a rule added later in the
  config sits earlier in the list and wins over this one.
- *Consequences, accepted:* help, compilation, magit and Vertico's buffer view now take
  the other pane rather than opening a third window. Vertico's is safe — its
  =vertico-buffer--setup= records =old-buf= of whichever window it lands in and puts it
  back on minibuffer exit; the =delete-window= path only runs for windows Vertico created.
- *Dedicated windows are never used* (side windows: treemacs, pdf-tools, Claude with
  =use-side-window t=). =window--display-buffer= silently *un*-dedicates a window it is
  handed, so the rule tests =window-dedicated-p= itself and falls back to the selected
  pane instead.
- *Verified* (2026-09-24): batch harness =local/tests/window-policy-test.el= (=emacs -Q --batch -l ...=,
  exit code = verdict; it lived in =/tmp= for a day, see the 2026-09-25 entry) reads the defun
  and the =add-to-list= *out of =config.org=* — no copy —
  then drives =display-buffer= through 9 cases: sole window, left selected, rightmost
  selected, buffer already visible, dedicated other pane, caller's =inhibit-same-window=,
  and no room to split. All pass; a third window never appears (window count asserted in
  every case). Live: new Claude session lands right, a second one replaces it in that pane.
  - *The next day:* the same cases are still there and still pass, in a harness that now has 26
    checks — the rule grew the reading case, and the doors that had been added on top of it were
    removed again. See the 2026-09-25 entry at the top of this section.
- *Correction to the entry above:* "on a frame too narrow to split, Emacs reuses an existing
  window" is true only with *two or more* windows. With a *sole* window,
  =split-window-sensibly= has a third branch — "if WINDOW is the only usable window on its
  frame... split it vertically disregarding the value of =split-height-threshold=" — which
  splits it *stacked*, below =split-width-threshold= (measured; case 6 of the harness).
- *Trick worth keeping:* an unbalanced =defun= in a =config.org= block fails silently —
  =read= (and therefore tangling) swallows the following forms, so the block still "works"
  while the =add-to-list= disappears into the defun's body. A batch script that =read=s the
  forms out of =config.org= and asserts *the next form is the one expected* catches it; it
  caught exactly this while the rule above was being written.

** Unblocking =doom sync -u= when it aborts on a package repo
=doom sync -u= runs in batch mode. If any straight repo under
=~/.config/emacs/.local/straight/repos/= is dirty, straight tries to prompt
interactively, gets EOF, and the whole sync aborts with:
=doom-package-error ... (end-of-file "Error reading from stdin")=. It only clears
one repo per run, so it can take a few rounds.

Scan all repos for dirty state before re-running:
#+begin_src sh
cd ~/.config/emacs/.local/straight/repos
for d in */; do d=${d%/}; [ -d "$d/.git" ] || continue; \
  s=$(git -C "$d" status --porcelain); \
  [ -n "$s" ] && { echo "### $d"; echo "$s"; }; done
#+end_src

Then, per kind of dirt:
- *Stray/untracked files that aren't part of the package:* check contents, then
  remove. (Seen: a stray =config.org= that was just a stale copy of the live one,
  plus a =myconfig.org= whose notes were already in =config.org=.)
- *Dirty (nested) git submodules* (e.g. tidal's =tidal-link/link= →
  =modules/asio-standalone=): reset recursively —
  =git -C <submodule-path> submodule update --init --recursive --force=.
- *Upstream =master= → =main= rename* (=fatal: couldn't find remote ref
  refs/heads/master=): simplest fix is to *delete the whole repo folder* and let
  =doom sync= re-clone it fresh on the current default branch:
  =rm -rf ~/.config/emacs/.local/straight/repos/<pkg>=. (Worked cleanly for
  =package-lint=.)

** After any =doom sync=
It prints "Restart Emacs for changes to take effect". A running Emacs keeps the old
code until you restart or run =M-x doom/reload=. Verify a fix against the rebuilt
=.elc= under =build-30.2/= (or the current Emacs version's build dir), not just the
repo source.

- *The user config is not one of those =.elc= files* (measured 2026-09-25): =find ~/.config/emacs
  -name config.elc= finds nothing. The straight build dir holds one directory per *package*, none
  for =$DOOMDIR/config.el=, which Doom loads as source — so an edit to =config.org= reaches a running
  Emacs only through =doom/reload= or a restart, and there is no stale bytecode to suspect when a

** flycheck's =org-lint= checker vs Org 9.8 — bug is upstream, do NOT shim
Symptom: opening any org file printed =Error from syntax checker org-lint: Wrong type

  (mapcar #'flycheck-error-line (seq-sort #'flycheck-error-< errors)))
#+end_src

=(evil-collection-…-setup)= or checker call returns "ok" even when it failed — check
=*Messages*= (=how-many=), not the return value.

** Parking a feature with =:tangle no= (and what it costs in =packages.el=)
Every src block in =config.org= tangles to =config.el= by default — that is the
=#+PROPERTY: header-args :tangle config.el= line near the top. A block carrying its own
=:tangle packages.el= or =:tangle no= wins over that default.

To park a feature — keep the code in the org file, stop it reaching the generated files —
mark *every* block of it =:tangle no=, including the bare =#+begin_src elisp= ones. Those
are the easy ones to miss: with no header arg they tangle into =config.el= by default.
The =** SAGE= section is parked this way (5 blocks, all =:tangle no=): Sage is not loaded,
but its code is still there to un-park.

Two costs worth remembering:
- *Tangling happens on save, and on =doom sync=.* The truth, read out of the code on
  2026-09-25: =bin/doom-sync:107= runs =(run-hooks 'doom-before-sync-hook)= before it
  synchronizes — only =--reload= skips that — and the =:config literate= module hooks
  =+literate-tangle-h= into it (=modules/config/literate/cli.el:18=), so a plain
  =doom sync= tangles =config.org= *first* and aborts the whole sync if that tangle
  fails (in batch, =+literate-tangle--sync= exits 3). That is why =config.el= — and
  =packages.el= — need not be committed: a fresh clone gets both from its first
  =doom sync=, before either is read. Saving *any* org file in =doom-user-dir= also
  retangles, in the background: =after-save-hook= runs =+literate-recompile-maybe-h= —
  measured 2026-09-25: a =tangle-config= process, "Done tangling 2 file(s)!", 0.4s.
  =M-x org-babel-tangle= is what does it *now*, without either of those.
  A =:tangle no= edit still stays invisible until some save, sync or tangle happens, and
  that tangle then flushes *all* pending org edits at once, which shows up as a
  surprisingly large =config.el= diff. Seen 2026-09-14: an 82-line diff that was mostly a
  park decided days earlier.
  - *Do not read =config.el='s timestamp to tell whether a save retangled:* org skips the
    write when the tangled text is unchanged, so a successful retangle of a comment-only
    edit leaves the file — and its mtime — exactly as it was. Ask
    =(process-live-p +literate-tangle--async-proc)= or read the = *tangle config*= buffer
    instead.
  - *Three wrong turns, written down so they are not taken again* (all on 2026-09-25):
    (1) "that save was a no-op" — =save-buffer= does nothing to an unmodified buffer, so
    no hook ran and the first check of this proved nothing; (2) "org wrote the file" — it
    had not: identical text means no write, which is why the mtime never moved; (3) "=doom
    sync= does not tangle" — it does, and =config.org='s own header carried that false
    claim for a day, because only the save path had been read.
- *Parking a =(package! …)= block un-declares the package.* =packages.el= is generated
  too, and =doom sync= runs autoremove from it — so the next sync *deletes* the package.
  Parking Sage's two =package!= blocks is what dropped =ob-sagemath= and
  =sage-shell-mode= on 2026-09-14. Parking code is free and reversible; parking its
  =package!= block costs a reinstall.

** Hydra menus draw their own table — stop hand-padding the hint
The two LaTeX menus (=SPC SPC l=, texlab/LSP, and =SPC SPC ?=, discover) no longer carry a
hand-drawn ASCII grid. An *empty body string* plus a =:column= on each group's first head
makes hydra build the table itself: =hydra--format-1= takes its =(string= docstring "")=
branch (=hydra.el:787=), which hands over to =hydra--hint= (=:614=) →
=hydra--generate-matrix= (=:1142=) → =hydra--hint-from-matrix= (=:1193=). That aligns the
columns, pads the doc column to the group's longest entry and rules the headers, so nothing
can drift when a head is added.

- Head order *is* column order, and a head with no =:column= silently inherits the one above
  it — a new head either gets a column or must sit inside the right group.
- *The doc strings set the column widths*: one long doc widens its whole column. The budget
  is the frame (=158= columns here); the texlab table renders at 132, so measure before
  growing one.
- *Colour is behaviour, not decoration*: =:color red= means the head does not exit the hydra,
  =:color blue= (the body's colour) means it does. Red therefore reads as "pressable again" —
  folds, the error walk, the on/off toggles. =:face= overrides only the displayed face
  (=hydra.el:653=) and changes no behaviour: that is how =K= (deletes the PDF) and =Q= are
  flagged, painted amaranth rather than red so that red keeps exactly one meaning.

Two hydra traps, both hit on 2026-09-14:
- Hydra *consumes* =:color= and rewrites the stored head with =:exit= instead
  (=hydra.el:637=, =:924=). Probing =(hydra--head-property head :color)= returns nil on a
  correctly coloured head — ask for =:exit=.
- =NAME/<command>-and-exit= symbols are generated for *every* head, and survive a
  redefinition in the same session, so =fboundp= on one cannot tell an exiting head from a
  staying one. It looked like a passing check; it would also have passed on a broken menu.

Read a menu without opening it: =defhydra= leaves =NAME/hint=, =NAME/heads= and
=NAME/keymap= behind, so =(eval (symbol-value 'brust-latex-lsp/hint))= prints exactly the
table the echo area would show.

** A keymap probe in a temp buffer sees none of the localleader keys
#+begin_src elisp
(with-temp-buffer
  (use-local-map LaTeX-mode-map)
  (setq major-mode 'latex-mode)
  (key-binding (kbd "SPC SPC e")))   ; => nil, for EVERY SPC SPC key
#+end_src
This returns nil for bindings that demonstrably work. Doom installs localleader keys per
*evil state* — =where-is-internal= reports them as =<normal-state> SPC SPC e=,
=<emacs-state> M-SPC m e= — and a plain temp buffer has none of that machinery active. On
2026-09-14 the table it produced read as "nothing is bound anywhere", which would have been a
false alarm of exactly the kind the audit was hunting.

What works instead: =where-is-internal= with the mode's keymap as its KEYMAP argument
(=nil= there means "the current buffer's active maps", not "every map"), plus one binding you
already know is good as the control.

** A minor-mode keymap outranks the major-mode one
=cdlatex-mode-map= bound =SPC SPC e= to =cdlatex-environment=, so any =SPC SPC e= added to
=LaTeX-mode-map= would be shadowed in every buffer where =cdlatex-mode= is on — and
invisibly, since the minor map is nowhere near the binding's source. When moving a
localleader key across that boundary, unbind it on the minor map too (=:localleader "e" nil=
in the =map!= block, the same shape as the backtick unbind just above it). That is what let
=SPC SPC e= / =SPC SPC E= mean insert / change a LaTeX environment with no shadowing left to
reason about, with =brust-LaTeX-env-change= finally passing =t= explicitly instead of the
broken =(not args)= that always inserted.

** pdf-tools: =pdf-sync-forward-search= has no autoload cookie
=pdf-tools/lisp/pdf-sync.el:651= defines it, but the file's only =;;;###autoload= is on
=pdf-sync-minor-mode= — so the symbol is *void* until something loads =pdf-sync=, which only
happens when the first PDF buffer opens. A key bound to it (=SPC SPC ?= → =g=, "PDF follows
this line") therefore signals =void-function= in a fresh session and works after the first
view. Fixed with an explicit =(autoload 'pdf-sync-forward-search "pdf-sync" nil t)= next to
the menu. A name that resolves is not a name that is *reachable*: check =fboundp= /
=commandp= on every command a menu head points at, not just the spelling.
